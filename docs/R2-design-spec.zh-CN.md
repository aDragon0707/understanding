# Lijie R2 设计规格

状态：方案阶段。本文件只描述设计，不修改全局 skill，也不修改 `source-snapshot`。

## 1. 设计总纲

`lijie` 不应该只是一个长篇讲解模板，也不应该假装 AI 能直接读取学习者隐藏的心理上下文。它应该是一套以证据为基础的学习协议，帮助学习者从“未知”逐步走向“已经验证的能力”。

目标不是单纯给出一个清楚的答案，而是形成：

```text
心智模型 + 可执行能力 + 错误地图 + 迁移证据 + 持久保持
```

Feynman 式解释、第一性原理拆解和知识结构映射仍然重要，但它们都不能单独证明学习者已经掌握。

## 2. 范围与非目标

### 2.1 处理范围

- 学习和内化概念、流程、系统、文章、课程和学科；
- 根据已观察到的前置知识和错误调整教学；
- 映射不同学科的原语、操作、约束和验证方式；
- 使用主动检索、主动生成、预测、反例、应用和迁移；
- 生成学习产物和简洁的学习记录；
- 支持一次性交付、互动学习和长期辅导；
- 区分来源事实、推断、不确定性和尚未覆盖的范围。

### 2.2 非目标

- 诊断人格或固定的学习风格；
- 没有证据时假装知道学习者的隐藏认知状态；
- 要求每个问题都走完整流程；
- 用摘要或类比替代领域实践；
- 因为一次对话成功就自动重写稳定的 skill；
- 未经用户控制就保存个人学习数据。

## 3. 总体架构

设计分成五层：

```text
稳定的核心协议
        ↓
学科适配器
        ↓
学习者状态
        ↓
学习证据与学习产物
        ↓
回归测试与受控演化
```

### 3.1 稳定的核心协议

未来的 `SKILL.md` 只保留不随学科变化的流程、触发描述、安全边界、模式选择、reference 导航和输出规则。按照 `skill-creator` 的原则，核心文件应保持精简，避免接近 500 行上限。

### 3.2 学科适配器

具体学科的拆解方法放在直接链接的 reference 中，例如 `code-learning.md`、`math-learning.md` 和 `history-learning.md`。不要把所有学科的细节塞进核心文件。

### 3.3 学习者状态

把学习者模型当作有证据支持的工作假设，而不是身份标签。状态可以包含：

```yaml
goal: explain | use | derive | critique | create | retain
prior_knowledge: []
observed_state: {}
misconceptions: []
tested_representations: []
current_hypotheses: []
next_probe: []
user_confirmed_preferences: []
```

掌握程度可以使用：

```text
unknown       未测试
fragile       脆弱
misconception 错误模型
prompted      需要提示
independent   可独立完成
transferable  可以迁移
retained      延迟后仍能保持
```

### 3.4 学习证据与学习产物

证据可以来自解释、预测、推导、实现、测试结果、反例、纠错或延迟检索。判断掌握程度时，应依靠证据，而不是依靠“听起来流畅”或“用户表示理解”。

### 3.5 受控演化

稳定规则只能经过“提出修改—回归测试—用户确认”后再升级。一次会话中的观察应留在学习记录中，不能悄悄写入 `SKILL.md`。

## 4. 分离三条运行轴

不要把输出长度、互动程度和严谨程度混成一个维度：

```text
Depth:        Light | Deep
Interaction:  One-shot | Interactive | Coaching
Verification: Informal | Rigorous | Source-backed
```

例如：

- 短概念笔记：`Light + One-shot`；
- 真正掌握数学概念：`Deep + Interactive`；
- 研究论文：`Deep + Source-backed`；
- 长期学习 Python：`Deep + Coaching`。

## 5. 核心学习状态机

```text
目标
  → 校准
  → 学科拆解
  → 构造模型
  → 学习者主动生成
  → 检索/应用/反例
  → 诊断缺口
  → 定向修复
  → 迁移
  → 延迟复习
  → 更新状态
```

### 5.1 目标契约

明确学习对象、目标能力、范围，以及什么才算成功。没有必要的问题不要阻塞流程，可以采用安全默认值。

### 5.2 校准

进行最小的基线测试，例如让学习者预测、解释、完成一个小应用，或检查前置知识。明确说出当前假设，并允许用户纠正。

### 5.3 学科拆解

当主题不只是一个短解释时，加载对应的 domain adapter。区分事实、定义、原语、假设、机制、约束、例子、边界情况和推论。

### 5.4 构造模型

根据任务选择具体例子、通俗机制、形式模型、图示、执行轨迹、证明骨架或来源论证。不要强行要求所有表示方式都出现。

### 5.5 学习者主动生成

在用户请求互动学习时，在直接公布结论之前，让学习者先预测、补全、解释、推导或在选项之间作出判断。反馈要足够及时，避免错误模型被固化。

### 5.6 验证

优先使用少量但有区分度的检查：

- 用自己的话解释；
- 预测下一步状态或结果；
- 应用到相邻案例；
- 比较两个相似案例；
- 找出边界或反例；
- 诊断一个故意写错的解答；
- 实际执行或实现操作。

### 5.7 修复与迁移

找到最窄的知识缺口，只重教这个缺口，然后重新测试。接着改变表面细节，同时保持或改变底层结构，检查是否真正理解了结构。

### 5.8 延迟复习

如果目标包含长期保持，应安排后续检索，而不能把当下的流畅感当作掌握。记录需要复习的内容和仍缺少的证据。

## 6. 学科适配器契约

每个学科 reference 都应回答以下问题：

```text
Objects        这个学科操作什么对象或主张？
Primitives     哪些东西不能再删，否则概念就不成立？
Operations     对这些对象可以做哪些有效操作？
Representations 具体、图示、形式化、可执行表示如何互相转换？
Assumptions    哪些条件必须成立？
Invariants     变化过程中什么必须保持不变？
Mechanisms     系统为什么会这样运行？
Constraints    方法在哪些地方会失效？
Failure Modes  常见误解和边界错误是什么？
Evidence       如何检查理解或正确性？
Transfer       什么相邻变体能检验结构性理解？
Prerequisites  需要先掌握什么？
Escalation     什么时候应该进入更难的表示或任务？
```

### 代码适配器示例

- 对象：值、状态、函数、模块、接口；
- 操作：调用、变换、组合、编译、执行、检查；
- 不变量：类型、契约、状态转换、资源所有权；
- 证据：测试、执行轨迹、日志、静态检查、性能测量；
- 迁移：改变需求、输入规模、异常路径或运行环境。

### 数学适配器示例

- 对象：定义、函数、集合、命题、证明；
- 操作：变换、构造、归纳、反证、分类、估计；
- 不变量：变换前后保持不变的性质；
- 证据：推导、证明、反例、条件检查、极限情况；
- 迁移：改变一个假设或边界条件后重新判断结论。

## 7. 方法组合，而不是天才人格模板

历史和认知研究应该用于选择方法，而不是制造人物崇拜式的学习模式：

```text
经验模式：     观察 → 归纳 → 模型
构造模式：     问题/矛盾 → 概念 → 推导 → 检验
对抗模式：     主张 → 反例 → 证据更新
执行模式：     规则 → 执行 → 测量 → 调试
迁移模式：     原任务 → 改变条件 → 比较结构
```

根据学习对象选择模式。数学证明、代码错误和历史主张不应该默认使用同一种顺序。

## 8. 语言策略

- 核心协议和 canonical field names 可以保留简洁英文，以减少术语漂移并保持兼容性；
- 面向用户的教学默认使用用户语言；本项目默认中文；
- 代码标识符、API 名称、数学符号和标准定理名保留原文；
- 使用稳定的中英术语表，不维护整份重复的中英文文档；
- 清晰度来自明确契约、例子、边界和测试，而不是来自英文本身。

## 9. Reference 加载策略

核心 skill 应直接链接每个 reference，并说明什么时候加载。reference 保持一层深度，只加载当前任务相关的内容。

未来可考虑的 reference：

```text
domain-adapter-template.md
code-learning.md
math-learning.md
history-learning.md
retention-protocol.md
source-evaluation.md
learner-state-schema.md
```

同一条规则不要同时重复写在 `SKILL.md` 和 reference 中。核心文件负责“选择什么”，reference 负责“这个变体怎么做”。

## 10. 学习产物

只生成对当前目标有用的产物：

- 学习契约；
- 紧凑心智模型；
- 第一性原理地图；
- 学科结构地图；
- 误解/错误记录；
- 掌握检查；
- 迁移任务；
- 延迟复习提示；
- 学习收据。

不要默认打印全部产物。一次性请求可以直接交付成品；互动请求应在最小有效检查处暂停。

## 11. 评测计划

在替换全局版本之前，用新鲜上下文运行代表性请求：

1. 数学：讲解一个定义，要求预测、证明或反例，再做条件改变后的迁移；
2. 代码：讲解一个小机制，追踪执行、诊断错误，再实现一个变体；
3. 历史或来源密集型材料：区分来源主张、推断、矛盾和证据质量；
4. 简单改写或翻译：确认不会不必要地触发学习闭环；
5. 明确要求一次性总结：确认不会强迫用户进入互动问答。

### 接受标准

- 能明确学习目标，或采用安全默认值；
- 深度学习时使用最小基线校准；
- 不推断固定学习风格；
- 选择相关学科适配器，而不是倾倒通用关系分类；
- 区分来源事实、推断和不确定性；
- 请求掌握时使用检索、应用或迁移；
- 根据实际错误诊断后再重教；
- 不强行生成不存在的关系类型或反馈环；
- 输出足够简洁，不吞噬无关上下文；
- 通过官方 skill validator，且不修改无关文件。

## 12. 实施顺序

1. 审阅并冻结本设计规格；
2. 定义 domain adapter 和 learner state 的 schema；
3. 从受保护的 source snapshot 创建新的 draft 目录；
4. 围绕状态机和 reference 导航重写 draft 的 `SKILL.md`；
5. 先加入两个学科适配器：数学和代码；
6. 建立代表性评测请求和学习收据；
7. 运行 validator 和 forward test；
8. 在演化日志中记录失败和被否决的方案；
9. 用户审阅后，才考虑替换全局版本。
